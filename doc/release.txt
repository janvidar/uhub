Making a uhub release
=====================

Why there is a procedure at all
-------------------------------

GitHub attaches "Source code (zip)" and "Source code (tar.gz)" to every tag
automatically. Those are a plain `git archive` of the superproject. Submodules
are gitlinks rather than files, so such an archive can never contain
third_party/exotic or third_party/quickjs -- there is no repository setting that
changes this, and the assets cannot be removed from the release page either.

An incomplete archive is not merely missing an optional feature: without exotic
a -DUHUB_TESTS=ON build fails outright, and without quickjs so does
-DJAVASCRIPT_SUPPORT=ON. The 0.8.0 release shipped with only those assets.

So every release also carries uhub-<version>-src.tar.gz, built by
scripts/make-dist.sh, which contains the submodule contents. The release notes
say plainly that the auto-generated links are incomplete.


Before tagging
--------------

The version is declared in three places and .github/workflows/release.yml
refuses to publish unless all three agree with the tag:

  - CMakeLists.txt          project (uhub VERSION x.y.z)
  - build.zig.zon           .version = "x.y.z"
  - ChangeLog               the top section heading, "x.y.z:"

Also decide deliberately whether to move the submodule pins
(git submodule update --remote, then commit the changed gitlinks); they are
part of what the release ships.


Tagging
-------

Tags carry no "v" prefix -- 0.8.0, not v0.8.0. The release workflow triggers on
[0-9]+.[0-9]+.[0-9]+*, so -rc suffixes are released the same way.

    git tag -a 0.8.1 -m "uhub 0.8.1"
    git push origin 0.8.1

That is all that is required. The workflow then checks the versions agree,
builds the archives, unpacks the tarball somewhere outside any git working tree
and builds it cold with -DUHUB_TESTS=ON -DJAVASCRIPT_SUPPORT=ON (so a missing
submodule fails the job rather than the user), and runs the test suite. It then
cross-compiles the five binary packages, runs the three that have a native
runner, regenerates SHA256SUMS over every asset and publishes.

The release is a draft until the last step, so it never appears with only part
of its assets attached. A failure anywhere leaves the draft in place for
inspection rather than publishing something half-built.


Fixing up a release that was already published
----------------------------------------------

Run the workflow by hand from the Actions tab ("Release" -> Run workflow) with
the tag name as input. When the release already exists the workflow uploads the
assets to it (--clobber) and leaves the existing notes alone, so the notes need
editing by hand to point at the tarball.

Equivalently, from a checkout:

    git checkout 0.8.0
    git submodule update --init --recursive
    scripts/make-dist.sh 0.8.0
    gh release upload 0.8.0 dist/* --clobber


Binary packages
---------------

Each release also carries a self-contained package per platform, built by
scripts/make-binary-dist.sh through the zig build (which statically links
LibreSSL and the vendored SQLite, and cross-compiles every platform from any
host):

    linux-x86_64    linux-aarch64    macos-x86_64    macos-aarch64    windows-x86_64

    scripts/make-binary-dist.sh <platform> [version]

Points worth knowing:

  - The Linux targets pin glibc 2.28 (RHEL 8 / Debian 10 era). Without the pin
    zig targets the build host's glibc and the binary will not start on anything
    older. musl is deliberately absent: the bundled LibreSSL's libcrypto.a is
    built without -fPIC and uhub links PIE, so that target does not link.

  - Built -Doptimize=ReleaseSafe, not ReleaseFast. This is a network daemon
    parsing attacker-controlled bytes before authentication, and aborting on a
    detected overflow beats being exploitable. -Dstrip=true as well, which is
    most of the download size.

  - The package is relocatable. etc/uhub.conf and etc/plugins.conf are the files
    from doc/ with their /usr/lib/uhub and /etc/uhub paths rewritten relative to
    the package root, and plugin names have their extension removed so the same
    config serves .so and .dll (the loader appends the platform's own; see
    plugin_add_extension in src/core/pluginloader.c). make-binary-dist.sh fails
    if an absolute path survives the rewrite.

  - Only linux-x86_64, macos-aarch64 and windows-x86_64 have a native GitHub
    runner, so those are the ones the release workflow actually executes.
    linux-aarch64 and macos-x86_64 ship cross-built and unrun.

  - Nothing is code-signed. macOS quarantines a downloaded package until the
    user clears the attribute, and Windows SmartScreen warns about an unknown
    publisher; RUNNING.txt in each package explains both.


Building an archive locally
---------------------------

    scripts/make-dist.sh [ref]        # ref defaults to HEAD

Writes dist/uhub-<version>-src.{tar.gz,zip} and dist/SHA256SUMS. The script
reads the submodule commits out of the tree of <ref> rather than out of the
working copy, so it produces the right archive even when the checkout is on
another branch; it refuses to run if a submodule it needs is not checked out.
Submodules marked "update = none" in .gitmodules are skipped deliberately --
that is how quickjs pulls in the ~50k-file test262 suite, which is not needed to
build.

Output is reproducible for repeated runs on the same host. The published
artifacts are the ones built by CI on Linux.


How a bad archive reports itself
--------------------------------

.gitattributes marks .uhub-archive-version as export-subst, so any git archive
(including GitHub's) has the placeholder in that file replaced by the describe
output, while a checkout keeps it literal. CMakeLists.txt uses that to tell the
two apart and to print advice the reader can act on: a checkout is told to run
git submodule update --init, while an unpacked archive -- which has no .git --
is pointed at the release tarball instead. The same value supplies the revision
in `uhub -V` when no git is available.
