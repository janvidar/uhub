# UHUB-2026-011 — NULL dereference when a client is disconnected by its own message

- **Severity:** Medium
- **Attack vector:** Network, by any user who can log in, no user interaction.
  On a hub that admits guests (the default) that is anyone
- **Impact:** The hub crashes, disconnecting every user (it is single-threaded)
- **CVSS 3.1 (suggested):** 5.9 — `AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:H`
  (`PR:L`, 5.3, with `registered_users_only = yes`)
- **Affected:** all uhub releases up to 0.8.1. The code path is unchanged
  since at least 0.6.0; older releases were not examined
- **Fixed in:** 0.8.2 (commit `f9cfeb8` on 0.8.x-stable; `7d31e16` on master)
- **Reported by:** found in an upstream code review

## Description

The reactor hands a client's connection one event mask per wakeup, and
`net_event()` (`src/core/netevent.c`) services the read side first, then the
write side:

```c
if (event & NET_EVENT_READ)
{
	flag_close = handle_net_read(user);
	if (flag_close) { hub_disconnect_user(...); return; }
}
if (event & NET_EVENT_WRITE)
{
	flag_close = handle_net_write(user);   /* user->connection may be NULL */
	...
```

Some message handlers disconnect the sender themselves and still return
success. Examples are a send-queue overflow caused by the sender's own message,
and a flood plugin's kick. `hub_disconnect_user()` closes the connection and
sets `user->connection` to NULL, but nothing tells `net_event()`. If the same
wakeup also reported the socket as writable, `handle_net_write()` runs for the
closed connection. When the send queue is empty, it then calls
`net_con_update(NULL, ...)` and the hub crashes.

The hub asks to be told about writability only while output to a client is
backed up, and the client decides how fast it reads. So a client can set up
both conditions. Hitting them in the same wakeup is a matter of timing,
hence `AC:H`.

## Remediation

Upgrade to **uhub 0.8.2** or later. `net_event()` no longer services the write
side of a user that the read side disconnected, and `handle_net_write()` does
nothing for a user without a connection.

No configuration or protocol change.

## Workarounds

None that close it. `registered_users_only = yes` limits the exposure to
registered users.
