# UHUB-2026-007 — Link command injection and ban removal through `!unban`

- **Severity:** High
- **Attack vector:** Network, requires an operator account. Command injection
  needs an established hub link; the ban-removal half does not
- **Impact:** An operator can inject arbitrary link commands that every linked
  hub runs as trusted, reaching effects normally reserved for admins. On its
  own hub, an operator can also lift a ban without naming the banned CID
  exactly
- **CVSS 3.1 (suggested):** 7.6 — `AV:N/AC:L/PR:H/UI:N/S:C/C:N/I:H/A:L`
- **Affected:** uhub 0.8.0
- **Fixed in:** 0.8.1 (commit `45b0de6` on 0.8.x-stable; `75f0aaa` on master)
- **Reported by:** Kcchouette (GitHub issue #129)

## Description

`!unban <target>` lifts a ban on a nick, CID or IP range, and on a linked hub
propagates it as `LUBN <target>`. The target comes from main chat, which the
hub decodes, so an escaped `\n` in it is a real newline. Two defects:

**1. Line injection.** Nothing checked the target for CR/LF before it was
written to the link:

```c
n = snprintf(buf, sizeof(buf), "LUBN %s\n", target);
```

The sibling `link_broadcast_ban()` already stripped CR/LF from its reason
field; `link_broadcast_unban()` did not. Every linked hub split the line at the
newline and ran what followed as a command from a trusted peer. The reporter
demonstrated injecting an `LRTE` that relays a message under an admin's SID to
a seeder bot, which then accepted an admin-only command.

**2. Truncated identifiers.** To remove a persisted ban, the target was copied
into fixed-size fields with `strncpy`, which cut it to 39 characters for the
CID:

```c
strncpy(ban.cid, target, MAX_CID_LEN);   /* a longer target loses its tail */
```

The storage plugin then deleted the ban matching that truncated value, so any
target that *begins* with a banned CID lifts that CID's persisted ban. Because
the propagation in defect 1 only happens when something was removed, the two
combine: a banned CID followed by a newline and an injected command both lifts
the ban and delivers the injection.

`!ban` is not affected; its target is the validated nick of a connected user.

## Remediation

Upgrade to **uhub 0.8.1** or later:

- an unban target containing CR or LF is refused before anything is removed
  or propagated;
- the storage plugin is offered only whole identifiers: the target as a nick
  if it fits, and as a CID only if it is exactly a 39-character base32 CID.
  Nothing is truncated;
- every line written to a link refuses an embedded CR/LF (see UHUB-2026-006).

The 0.8.1 link changes also stop a peer from routing messages as a user it
does not own, which closes the escalation path the reporter demonstrated even
on its own.

## Workarounds

Only grant operator rights to trusted users. On hubs that do not link, the
command-injection half does not apply.
