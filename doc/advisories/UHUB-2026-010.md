# UHUB-2026-010 — `auth_proxy` slave applies a late master reply to the next login on the same SID

- **Severity:** Medium
- **Attack vector:** Network, unauthenticated, no user interaction. Only hubs
  with `auth_proxy = 1` and an established link to their auth master
- **Impact:** A client logs in under a nick that is registered on the master,
  without its password, by reusing the SID of an earlier login of its own
- **CVSS 3.1 (suggested):** 6.5 — `AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:H/A:N`
- **Affected:** uhub 0.7.0 – 0.8.1, when `auth_proxy` is enabled
- **Fixed in:** 0.8.2 (commit `7dcd698` on 0.8.x-stable; `d20a976` on master)
- **Reported by:** found in an upstream code review

## Description

An `auth_proxy` slave asks its master about each login: `LACQ <sid> <nick>`
asks whether the nick is registered and with what credential, and
`LVFY <sid> ...` asks it to check a password. The master echoes the first
field back in `LACR` / `LVRS`, and the slave used it to find the waiting login:

```c
LIST_FOREACH(struct hub_user*, user, g_auth_pending,
{
	if (user->id.sid == sid)   /* the SID is the only key */
	...
```

A SID identifies a user only while that user is connected. When a client
leaves, its SID is freed and can be given to the next client to connect. If
the master's answer for the first login is still on its way, it then settles
whichever login holds that SID when it arrives.

A client that controls both logins can use this. It asks about an
unregistered nick, leaves, and reconnects under a registered nick before the
master's answer arrives. If the new login gets the same SID, the late `guest`
answer for the first nick settles it, and the client is logged in under the
registered nick without being asked for the password. The credential is
`guest`, so the client gains no operator rights. But other users see the
registered nick, and the nick's owner can no longer log in while it is held.

The attacker has to win a race against the link round-trip and get the same
SID back, hence `AC:H`.

## Remediation

Upgrade to **uhub 0.8.2** or later. Each request now carries a tag made of the
SID and the hub's per-connection id (`LACQ AAAB.0000001f <nick>`), and only a
reply with the same tag settles a login. A reply for a login that has left,
or one carrying a bare SID, settles nothing. See `doc/linking.txt`.

The master echoes the field without reading it, so a 0.8.1 master answers a
0.8.2 slave correctly. Slaves and the master can be upgraded one at a time.
Until a slave is upgraded, it remains affected.

## Workarounds

- Set `auth_proxy = 0` on reachable slaves (they then log users in locally,
  without the master's accounts).
- Otherwise, restrict who can reach the slave's client port.
