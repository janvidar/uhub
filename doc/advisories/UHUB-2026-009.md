# UHUB-2026-009 — Use-after-free in the `auth_proxy` slave's pending-login registry

- **Severity:** Critical
- **Attack vector:** Network, unauthenticated, no user interaction. Only hubs
  with `auth_proxy = 1` and an established link to their auth master
- **Impact:** Heap use-after-free. At minimum the hub crashes for every user
  (it is single-threaded); the freed user is written through, so memory
  corruption beyond a crash cannot be ruled out
- **CVSS 3.1 (suggested):** 9.8 — `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`
- **Affected:** uhub 0.7.0 – 0.8.1, when `auth_proxy` is enabled
- **Fixed in:** 0.8.2 (commit `f9cfeb8` on 0.8.x-stable; `7d31e16` on master)
- **Reported by:** found in an upstream code review

## Description

A hub with `auth_proxy = 1` keeps no accounts of its own. While a login waits
for the master, the slave keeps the user in a registry of pending logins
(`g_auth_pending` in `src/core/link.c`): `LACQ` asks whether a nick is
registered, and `LVFY` asks the master to check a password. Each request
appended the user to the registry:

```c
if (link_sendf(master, "LVFY %s %s %s %s\n", ...) < 0)
	return 0;
if (g_auth_pending)
	list_append(g_auth_pending, user);
```

Nothing stopped the same user from being appended twice. A client logging in
with a registered nick can send its password again while the first `LVFY` is
still with the master. When the client then disconnects, the slave forgets it
once, which removes one of the two entries:

```c
void link_auth_pending_forget(struct hub_user* user)
{
	if (g_auth_pending)
		list_remove(g_auth_pending, user);   /* removes one match */
}
```

The other entry points at the user after it is freed. Each later `LACR` or
`LVRS` from the master walks the registry and reads every entry's SID, which
reads freed memory. If the freed entry matches, the reply is applied to it,
which writes to freed memory.

Any nick registered on the master will do, since the client only needs to be
asked for a password. It needs no password of its own.

The same release fixes a related double free on linked hubs, which needs an
operator to trigger it. When a remote user (one on another node) was kicked
locally, it stayed in the user manager until its queued QUIT event ran. If
the peer's `LQUI` arrived or the link dropped in the meantime, the link layer
freed the user, and the queued events then freed it again.

## Remediation

Upgrade to **uhub 0.8.2** or later. A user is now in the registry at most once,
and forgetting a user removes every entry for it. A remote user who is
disconnected locally now leaves the user manager at once, so the link layer
can no longer find it and free it a second time.

No configuration or wire-format change. Slaves and the master can be upgraded
one at a time.

## Workarounds

- Set `auth_proxy = 0` on reachable slaves (they then log users in locally,
  without the master's accounts).
- Otherwise, restrict who can reach the slave's client port.
