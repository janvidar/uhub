# UHUB-2026-005 — Hub-link authentication bypass by challenge reflection

- **Severity:** Critical
- **Attack vector:** Network, unauthenticated, no user interaction. Only hubs
  with linking enabled (`link_secret` set, including multi-worker mode)
- **Impact:** A peer without the shared secret becomes a fully trusted linked
  hub. It can read federated traffic, inject users and messages, and add or
  lift bans across the cluster
- **CVSS 3.1 (suggested):** 9.8 — `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`
- **Affected:** uhub 0.7.0 – 0.8.0, when `link_secret` is set
- **Fixed in:** 0.8.1 (commit `45b0de6` on 0.8.x-stable; `75f0aaa` on master)
- **Reported by:** Kcchouette (GitHub issue #127)

## Description

Linked hubs authenticate each other with a challenge-response on the shared
`link_secret`. Each side sends `LCHA <nonce>`, the other answers
`LRES <response>`, and an `LACK` acknowledges a verified answer. In 0.7.0–0.8.0
the response was `base32(tiger(secret || nonce))`. It depended only on the
secret and the nonce, and a hub answered **any** `LCHA` it received, including
its own nonce sent back to it:

```c
if (strncmp(line, "LCHA ", 5) == 0)
{
    link_auth_response(secret, line + 5, resp);   /* answers whatever it is sent */
    return link_sendf(link, "LRES %s\n", resp);
}
```

An attacker therefore never needs the secret:

1. Connect to the hub's normal client port and send `LCHA <anything>`. The
   probe hands the connection to the link handler, and the hub sends its own
   challenge `LCHA <N>`.
2. Send `LCHA <N>` back. The hub replies with `LRES base32(tiger(secret || N))`,
   the correct answer to its own challenge.
3. Present that answer as `LRES`, then send `LACK`. The hub marks the peer
   verified and establishes the link.

The handshake also accepted repeated and out-of-order messages, and handshake
messages after the link was established.

## Impact

An established link is a trusted peer. Through it the attacker can:

- read roster updates, public chat and searches relayed across the cluster;
- inject remote users with arbitrary identities, and route messages to local
  users;
- ban or unban anyone cluster-wide (`LBAN` / `LUBN`), which disconnects
  matching users;
- answer authentication queries on a hub that proxies its logins to this one
  (`auth_proxy`).

## Remediation

Upgrade to **uhub 0.8.1** or later. The link handshake is now version 2:

- the response is a truncated HMAC-SHA256 over the sender's role (connecting or
  accepting side) and both nonces, so a hub's answer to its own challenge, or
  its answer played back to it, no longer verifies;
- each side accepts exactly one `LCHA`, then one valid `LRES`, then one `LACK`.
  A malformed nonce, our own nonce echoed back, a repeat, an out-of-order
  message, or any handshake message after establishment closes the link.

**This is a protocol change.** A 0.8.1 hub cannot link with an older one, so
every hub and worker in a cluster must be upgraded together. There is
deliberately no fallback to the vulnerable v1 handshake. See
`doc/linking.txt`.

### Related hardening in the same release

These assume an authenticated peer, so they mattered most in combination with
the bypass above:

- A peer can only route messages (`LRTE`) as users it introduced over that same
  link. Before, it could send as any local user (an operator, say, whose
  private messages a bot obeys) or as a user on another node.
- An `auth_proxy` slave accepts `LACR` / `LVRS` replies only from its auth
  master, not from any linked peer.
- `LDSC` (topic) must be a single escaped token; a space could add fields of
  the peer's choosing to the hub INF that every client receives.
- `LBAN` escapes the nick. Before, banning a nick with a space in it banned
  the nick's first word on the other hubs, and over-long fields were silently
  truncated.

## Workarounds

- Leave `link_secret` empty on hubs that do not link; this rejects every link
  connection.
- Otherwise, firewall the hub port so that only the other cluster members can
  reach it. The link handshake shares the client port, so this also restricts
  clients unless the hubs run behind separate interfaces or addresses.
