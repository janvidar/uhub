# UHUB-2026-008 — `exclusive` auth mode does not keep unknown nicks out

- **Severity:** Medium
- **Attack vector:** Network, unauthenticated, no user interaction. Only hubs
  that rely on an auth plugin's `exclusive` option (rather than
  `registered_users_only`) to keep unregistered users out
- **Impact:** An unregistered nick logs in as a guest on a hub configured to
  admit only its registered accounts: it sees the user list, chat and
  searches, and can take part as a guest. It gains no operator rights
- **CVSS 3.1 (suggested):** 6.5 — `AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:N`
- **Affected:** uhub <= 0.8.0
- **Fixed in:** 0.8.1 (commit `5ff21d7` on 0.8.x-stable; `c01fe6f` on master)
- **Reported by:** Kcchouette (GitHub issue #130)

## Description

`exclusive` is documented as "users not in the database are rejected
outright". Three things defeated it:

1. **mod_auth_sqlite ignored it for logins.** `get_user` returned `st_default`
   ("not mine, ask the next plugin") for an unknown nick whatever the flag
   said; the flag only gated deleting accounts and persisting bans.
2. **A refusal became a guest login.** mod_auth_simple does return `st_deny` in
   exclusive mode, but `acl_get_access_info()` turned anything other than
   `st_allow` into "no account", and the login path makes "no account" a guest:

   ```c
   if (plugin_auth_get_user(hub, name, info) != st_allow)
   {
       hub_free(info);
       return NULL;            /* st_deny looks the same as st_default */
   }
   ```
3. **A guest record beat a refusal.** With mod_guest_passwd loaded,
   `plugin_auth_get_user()` returned the guest-level record ahead of another
   plugin's refusal, so the unknown nick logged in by giving the guest password.

On an `auth_proxy` slave the same collapse meant the master could never pass
a refusal on: it answered `guest` for every unknown nick.

A related defect: when mod_auth_sqlite's lookup failed (database locked or
damaged), it also answered `st_default`, letting a registered nick log in as
a guest without its password.

## Remediation

Upgrade to **uhub 0.8.1** or later:

- an explicit refusal from an auth plugin rejects the login ("Hub is for
  registered users only");
- a real account from any plugin still wins, but a refusal now beats a
  guest-level record from another plugin, whatever the plugin order;
- mod_auth_sqlite with `exclusive=1` refuses nicks not in its database. A
  failed lookup, or a record with no credential, refuses too. A database with
  no users table yet (a fresh install) still means "no accounts";
- an auth master answers `LACR <sid> none` for a refused nick, and the slave
  rejects the login. A slave that cannot reach its master still admits
  guests, as before.

**Behaviour change:** a hub that combines `exclusive` with mod_guest_passwd
admits no guests any more, and a hub with mod_auth_sqlite `exclusive=1` starts
refusing unknown nicks. That is the documented meaning of the option; remove
`exclusive` to keep admitting guests. With `auth_proxy`, upgrade the slaves
too, or they will not enforce the master's refusal (0.8.1 has to be deployed
cluster-wide anyway, for UHUB-2026-005).

## Workarounds

Set `registered_users_only = yes`, which refuses every login without an
account independently of the auth plugins.
